# WizRust101-DB specifications

> WizRust101-DB is fully vibe coded.

## Purpose and observed data

The CLI creates a database of player-visible Wizard101 location names from extracted data in `raw/`. Canonical zone identifiers are not display names: names may differ entirely, and several interiors intentionally resolve through a map assigned to a parent area.

The verified global association resource is `raw/misc/Root/DoodleMapMap.xml`. Its serialized records contain a map resource path such as `|GUI|WorldData|Maps/AQ_Z01_Palace_of_Immortals.xml` followed by one or more canonical zone paths such as `Aquila/Interiors/AQ_Z01_Apollo_Room`. Each referenced map XML contains a localization key such as `Zone_00001124`. `raw/misc/Root/Locale/en-US/Zone.lang` maps that numeric key to the map title `Mount Olympus`. This chain was verified against Aquila, Azteca, and reference examples, including exceptional interior identifiers.

Candidate sources retain provenance. The current-zone localization field must come only from the header field immediately following the canonical path field in `gamedata.bin`: path property marker `f8 63 69 81`, its `u16` byte length and path bytes, the four-byte header separator, then property marker `6e ec f6 74`, its `u16` byte length, and the complete field value. Do not scan farther into the file for another localization reference. A direct `Zone_########` header value resolves through `raw/misc/Root/Locale/en-US/Zone.lang`; a direct `Housing_########` value resolves through `Housing.lang`. These exact-path header fields identify the zone or housing title and are treated as verified specific-name candidates. This was checked on the Hall of the Ice Forge, whose direct Zone value agrees with the independently associated map title, and on housing zone headers with localized house titles. Clearly non-display test labels such as `TEST-Interior` remain unusable. A `WizardZone_...` header value resolves by exact numeric or symbolic key through `WizardZone.lang`; symbolic locale records may be either key/blank/value or key/description/value. An unlocalized symbolic suffix is retained in diagnostics but never prettified or emitted as a name. WizardZone values can identify a parent region, an instance, or an event phase, so a localized header value is a fallback rather than verified display evidence. A shared-map candidate comes from the explicit DoodleMapMap-to-map-resource-to-`Zone_########`-to-`Zone.lang` chain and may likewise be broader or stale.

A Compass POI title can be assigned to a child zone only with the complete chain: parent POI trigger and matching POI volume -> localized `WizardCompassLocs_########` key -> named parent teleport/portal -> matching explicit child exit identifier. The child relationship must also be supported by raw zone/resource association; matching strings alone are insufficient. A unique proven Compass POI name wins. Generic POI and entry-text labels are supporting evidence only and never candidates for display names.

Selection follows this priority: (1) one proven Compass POI/child name; (2) a direct `Zone_` or `Housing_` current-zone header localization; (3) one trustworthy shared-map name when no WizardZone candidate conflicts; (4) the exact localized value from the zone-header WizardZone field as an explicitly unverified fallback; (5) `Unknown`. A direct current-zone header value remains selected when a broader map candidate disagrees, and the conflict is recorded. If WizardZone and shared-map candidates conflict without evidence deciding them, choose the header WizardZone only as `unverified_fallback`, and retain the conflict in diagnostics. Multiple conflicting proven POI candidates are recorded as ambiguity; a direct current-zone header can resolve them, otherwise use a usable WizardZone header fallback if available, else `Unknown`. Reject clearly malformed or unrelated map localization, including a label that identifies a different world/zone. Never prettify an identifier or use the reference as a name source. `ZoneLocName.lang` remains unsupported for zone display-name resolution absent a proven zone-specific relationship.

The comparison oracle defaults to `tmp/zones.json` and can be overridden with `--reference`. It is validation input only and never supplies generated names.

## World-name evidence research

The extracted English `raw/misc/Root/Locale/en-US/WorldNames.lang` is the preferred and verified source for player-visible world labels. It contains explicit internal-key/display-value pairs, including `WizardCity` -> `Wizard City`, `DragonSpire` -> `Dragonspyre`, `G14_DM` -> `Castle Darkmoor`, and `G14_SB` -> `Kembaalung Village`. For each canonical path, use its exact first path component only as a lookup key in this localization table; emit the localized value only when that exact key has a usable non-empty display value. `AllWorlds` is a UI grouping and `Crafting` is annotated in the locale data as not being an actual world, so neither is accepted as a world label. This does not assume that the path component is itself a display name and does not prettify it. The exact localized key/value relationship is recorded as the world source.

Research of the extracted en-US resources also supports two narrowly scoped canonical aliases when `WorldNames.lang` has no usable value for the root. `G14_HS` resolves to `Zigazag`: `raw/misc/g14_hs/G14_HS-WorldData/WorldTPTrans.xml` names a `ZigZag World Transition` and explicitly references the `G14_HS` package; `WorldHubZones.xml` associates `G14_HS/HS_Z01_ZigazagUpper` with `WizardZone_00001125`, whose en-US value is `Upper Zigazag`. The world spelling follows the localized form. `GrizzleheimLite` resolves to `Grizzleheim`: `raw/grizzleheim/GrizzleheimLite-WorldData/WorldTPTrans.xml` contains the `Grizzleheim World Transition` label and explicitly references the `GrizzleheimLite` package; `Grizzleheim` itself is an en-US `WorldNames.lang` key and display value. These aliases are kept as explicit, provenance-bearing rules.

`OrderedWorlds.lang` is a localized ordering list for a subset of worlds; it does not provide a complete canonical-path association and is not used to infer missing labels. `WorldHubZones.xml` contains serialized hub/group records, including records that deliberately group housing, holiday, pet derby, heroic dungeon, and other unrelated canonical paths under Wizard City or another hub. Those records are not a reliable general current-zone-to-world mapping. Apart from the specific `G14_HS` alias chain above, the records do not assign a world. World transition names for gauntlets/events can refer to the activity rather than its canonical world; for example, `MonthlyEvents` has a Sinbad gauntlet transition that references Wizard City assets, which is insufficient to label all its canonical paths as Wizard City. Likewise, housing groups and raw directory names do not establish a player-visible world.

World resolution follows this order: (1) exact usable `WorldNames.lang` value; (2) an explicit evidence-backed canonical alias; (3) preserve recognized player-facing content roots (`PetDerby`, `Raids`) unchanged; (4) for any other non-empty root that would otherwise be `Unknown`, preserve the first canonical path component unchanged, except any root beginning with `Housing` becomes `House`. These final fallbacks apply only after localization and alias resolution, so they do not change any successfully resolved world. Do not prettify or otherwise transform fallback roots. The Housing rule includes `Housing`, `Housing_*`, and any other root with the `Housing` prefix. Alias evidence is documented in [world-root-audit.md](world-root-audit.md). No parent-world inference is made from a nested path or validation reference. World resolution is independent of zone-name resolution and cannot change a selected zone value.

The resolver records `localized`, `canonical_alias_fallback`, `raw_root_fallback`, `root_fallback`, `house_fallback`, or `unknown`, with per-entry provenance. For this 3,346-entry extraction: 2,643 are localized, 51 use canonical aliases, 19 preserve recognized player-facing roots, 138 use unchanged roots, 495 use `House`, and 0 remain `Unknown`. There are 35 distinct final world names. The root-by-root evidence audit is in [world-root-audit.md](world-root-audit.md). Counts describe this extraction and can change with a different raw snapshot.

## Discovery and association

- Input defaults to `./raw`, overridable with `--input`.
- Recursively discover directories with a direct child `gamedata.bin`; do not follow symlinks. Sort discovered directories before processing.
- Extract the canonical key from the first readable slash-delimited path in `gamedata.bin`. Preserve every component, punctuation, and case.
- Parse `DoodleMapMap.xml` as a binary serialized resource. In the inspected serialization, a canonical path follows a `|GUI|WorldData|Maps/<asset>.xml` reference; associate the path with the nearest preceding map reference only when the byte gap is at most 64 bytes. This is a format-derived association heuristic, not a general XML parser. Do not infer relationships from similar filenames or `_ZNN` prefixes.
- Resolve each referenced map path below `raw/misc/GUI-WorldData/Maps/`. Use the first `Zone_########` key in the referenced map resource. In inspected multi-key maps, this leading key is the map title; later keys can identify other map content and do not override it.
- Parse the English `Zone.lang` UTF-16LE localization table into numeric-key/display-text pairs. Use the exact localized string, without prettifying or correcting it.
- Extract the canonical path from its header field, then read exactly the immediately following `6e ec f6 74` localization property field. Preserve its complete raw value in diagnostics. Resolve a complete `Zone_########` value only through `Zone.lang`, a `Housing_########` value only through `Housing.lang`, and a `WizardZone_...` value only through `WizardZone.lang`. In WizardZone.lang, accept numeric/symbolic keys in key/blank/value records and symbolic keys in key/description/value records. Never search later serialized fields when the header value is malformed or missing. An unmapped key is not a name.
- Keep direct Zone/Housing header, WizardZone, shared-map, and proven Compass names as independent candidates. Select a unique proven Compass POI child name first, then a direct current-zone Zone/Housing header localization as verified. Otherwise select a unique shared-map name if WizardZone is absent or agrees. When only map/WizardZone conflict or no usable map title exists, prefer a localized value from the actual zone-header WizardZone field only as `unverified_fallback`. Reject obvious test labels such as `TEST-Interior`. If no localized usable candidate exists, emit the final `/`-delimited canonical path component unchanged as a `canonical_leaf_fallback`, with `unverified_fallback` confidence. Never prettify symbolic keys or canonical paths.
- Derive Compass POI candidates from parent `triggers.xml`, parent `volumes.xml`, and child `triggers.xml`/`volumes.xml`. Require a POI trigger, its same-token POI volume, one localized `WizardCompassLocs_########` key in the trigger record, a parent teleport target with the exact same token, a child `Teleport-Exit<token>` identifier, and a shared explicit DoodleMap map association between parent and child. Select a unique proven POI child name ahead of map and WizardZone candidates. If proven POI names conflict, mark the zone ambiguous; a direct current-zone header may resolve that ambiguity, otherwise retain a usable WizardZone fallback or emit `Unknown`.
- A zone may have more than one explicitly associated map resource. If they resolve to different titles, retain the candidate set and mark it ambiguous unless raw relationships establish which title is current. A proven unique POI candidate still wins. Reject malformed/unrelated map labels; do not select a remaining WizardZone candidate merely because the map title was rejected or missing.
- Explicit links in `DoodleMapMap.xml` support parent-map inheritance; `_ZNN` similarity does not. Preserve extracted names even when they differ from the human-curated reference.

## Output and deterministic behavior

`out/zones.json` is the RPC-facing database: a UTF-8, two-space-indented JSON object mapping every discovered canonical path to an object with `world` and `zone` string fields. The world field follows the localized/alias/allowlisted-raw/unknown priority above. The zone field is the best available extracted display name or the unchanged canonical leaf when no candidate is supported; zone values are never `Unknown`. No discovered path is omitted because a name is uncertain. The sidecar diagnostics are not part of this schema and cannot alter selected names or JSON bytes:

```json
{
  "Aquila/AQ_Z00_Hub": {
    "world": "Aquila",
    "zone": "Garden of Hesperides"
  }
}
```

Sort keys lexicographically and terminate with a newline. Create the output directory when missing. Diagnostics are written separately and never feed back into generation. `generate` does not read the reference oracle, even when the configured reference path is missing. Refuse an output JSON or diagnostics path beneath the canonical input root; generation never writes to or modifies `raw/`. No identifier-derived fallback is permitted.

Write a separate deterministic diagnostics sidecar beside the output as `<output-stem>.diagnostics.json` (for example, `out/zones.diagnostics.json`). For every discovered path it records candidates with source and provenance, the selected zone candidate and confidence, the emitted zone name/source/confidence/provenance, the world lookup key/name/source/confidence/provenance, the exact immediate header field value and its localized value when available, candidate conflicts, and ambiguity/unresolved reasons. World source is `localized`, `canonical_alias_fallback`, `raw_root_fallback`, `root_fallback`, `house_fallback`, or `unknown`; world confidence is `verified` for a `WorldNames.lang` result, `fallback` for any fallback, and `unknown` for an unknown world. Zone confidence remains `verified` for proven Compass, direct Zone/Housing header, or uncontested shared-map selections and `unverified_fallback` for header WizardZone or canonical-leaf selections. A validation reference never changes either field or its selection.

## Comparison and conflicts

`compare --reference PATH` writes both generated JSON and its diagnostics sidecar and reports candidate counts, selected counts by confidence, exact zone-name reference matches, mismatches, unresolved reference zones, ambiguous candidates, and generated-only zones. It accepts the existing path-to-string reference shape and object values containing a string `zone` field; only the reference zone-name field is compared. Zones without a resolver-selected candidate count as unresolved even though the RPC output carries the canonical leaf. Per-zone diagnostics identify each available source with provenance, selected source/confidence, candidate disagreements, and reference conflicts. A reference string is validation-only and never supplies a candidate or changes selection. The default reference is `tmp/zones.json`.

For the checked-in raw snapshot, the before/after zone counts are unchanged: 3,346 entries, 1,240 verified names, 2,080 unverified WizardZone fallbacks, and 26 unresolved paths. The 26 unresolved outputs now contain their canonical leaf with explicitly unverified provenance. All 3,320 previously resolved zone values are unchanged (zero regressions).

Malformed CLI arguments, unreadable required metadata, duplicate canonical keys with conflicting evidence, or output failures are fatal. Individual zones with incomplete or conflicting mapping evidence are reported in the diagnostics sidecar and still appear in RPC output with either the chosen localized candidate or the unchanged canonical leaf fallback.

## Tests and validation

Unit and fixture integration tests cover proven direct/child resolution, canonical-leaf fallback provenance, the Pit of the Noxii POI chain, direct Zone/Housing header localization, numeric and symbolic WizardZone header keys, description-bearing symbolic localization rows, ignoring later WizardZone references, conflicts, invalid map labels, special interiors (Gorgon Cave, Vestrilund, Zeus Exalted Duel, Altar of Kings, Triton, Stonegaze's Antichamber), localized world values, canonical aliases, unchanged root fallback, and Housing-to-House fallback, reference comparisons, deterministic output despite diagnostics changes, and generation without an oracle. Run `cargo fmt --check`, `cargo clippy --locked -- -D warnings`, `cargo test --locked --all-targets`, and `cargo build --locked`. From a clean clone, first run `cargo build --locked` and `cargo test --locked`; extracted game data is not committed and must be placed in `raw/`. Generate with `cargo run --locked -- generate --input raw --output out/zones.json`; this also writes `out/zones.diagnostics.json`. The generated `out/zones.json` is consumed directly by WizRust101-RPC as a path-to-object database, where each value contains `world` and `zone` strings; zones without localized/resolved names carry their canonical leaf. Validate separately with `cargo run --locked -- compare --input raw --reference tmp/zones.json`; the comparison uses only the reference zone field and supports both the previous path-to-string format and the new object format.

## Known limitations

- `DoodleMapMap.xml` and its map assets only resolve paths represented in that resource; all other canonical keys remain unresolved.
- WizardZone and Compass POI resources are not guaranteed to exist for every zone. A header WizardZone localization may be broad or phase-specific; fallback confidence is recorded explicitly and is not a claim that the value is the in-game display name.
- `tmp/zones.json` is a mutable validation fixture, not a source of names. Its contents and count can change independently of extracted game data.
- Extracted English is authoritative for this output; localized strings in other supported client languages are not selected automatically.
